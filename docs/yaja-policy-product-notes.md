# 야자시 정책 — 제품·엔진 정리 (운세위키 QA 확정 반영)

운세위키는 **야자시 적용 / 미적용**을 사용자가 고른다.  
목표는 “역사적으로 어느 쪽이 옳다”가 아니라, **우리 엔진이 위키의 어느 토글에 대응하는지**를 고정하고, **향후 옵션화 시 최소 분기**를 남기는 것이다.  
(본 문서는 **정책·설계 문서**만 갱신. 코드 변경 없음.)

---

## 0. 운세위키 QA로 확정된 규칙 (2026-05 기준)

| 항목 | 확정 내용 |
|------|-----------|
| **子 시 시작** | **23:30 KST**부터 子 구간 |
| **적용 (당일)** | 23:30 이후에도 **양력 달력 “당일” 일주** 유지 (晚子를 당일 일주에 붙임) |
| **미적용 (다음날)** | **23:30부터** 일주를 **익일 양력 일자** 기준으로 본다 (晚子 → 익일 일주) |

**관측 예 (양력 2001-01-01, 23:30 KST):**

| 위키 모드 | 일주(확정 관측) |
|-----------|-----------------|
| **적용 (당일)** | **갑자** |
| **미적용 (다음날)** | **을축** |

위키 **子 진입 시각(23:30)** 은 현재 엔진의 한국형 시진(`korean-hour-pillar.js`)과 **동일**하다. 남는 차이는 **일주를 당일에 둘지·23:30부터 익일로 넘길지**뿐이다.

---

## 1. 현재 엔진은 어떤 기준인가

### 일주(및 `manseryeok` 일간)

- `calculateFourPillars`에 넘기는 생년월일은 **양력 벽시계 연·월·일** 그대로이며, **23:xx~23:59라도 달력 날짜를 바꾸지 않는다.**
- 즉 일주는 **“양력 자정(00:00)에서 날짜가 바뀌는” 일반 달력 기준**이다.
- **23:30에 일주를 익일로 당기지 않는다.**

### 시주(한국형 30분 시진)

- **23:30~익일 01:29** 를 **子**로 본다 (위키 子 시작과 동일).
- 시천간은 **그 시점의 일간(`pillars.day.heavenlyStem`)** 과 五鼠遁으로 정한다.
- 일간은 **위의 자정 기준 당일 일주**이므로, **23:40에도 “양력 1일” 일간**을 쓴다.

### 위키 토글과의 대응 (최종)

| 위키 모드 | 일주 귀속 | 현재 엔진과의 관계 |
|-----------|-----------|---------------------|
| **적용 (당일)** | 23:30 이후도 **당일** 일주 | **일주 귀속은 동일** (양력 당일 고정) |
| **미적용 (다음날)** | 23:30부터 **익일** 일주 | **불일치** — 엔진은 23:30에 일주를 넘기지 않음 |

**한 줄:** 현재 엔진은 운세위키 **「야자시 적용 (당일)」** 과 **일주·子 시작(23:30) 측면에서 가장 가깝다.**  
**「미적용 (다음날)」** 과는 **일주(및 그에 따른 시천간)** 에서 어긋난다.

> 시주 한 글자까지 위키 적용 모드와 **항상 동일**하다고 단정하지는 않는다(일간·五鼠遁·표시 격자 등 추가 QA 여지). 다만 **관측된 2001-01-01 23:30 일주(갑자 vs 을축)** 기준으로 보면, 엔진은 **적용(당일)** 쪽과 정렬된다.

## 2. 운세위키와 동일 UX를 가리면

- 위키가 **적용 / 미적용**을 노출하므로, **동일한 선택지**를 API·UI에 두는 것이 사용자 기대와 맞다.
- **기본값**은 PM/운영에서 확정: 위키 신규 기본이 어느 쪽인지 한 번 더 확인한 뒤, **엔진 기본을 위키 기본에 맞추거나**, 엔진을 고정한 채 **UI에서만 위키와 다른 경우 안내**를 둘 수 있다.

---

## 3. 옵션화할 경우 영향 범위

| 영역 | 영향 |
|------|------|
| **일주** | **미적용(다음날)** 시, `23:30 <= 시각 < 익일 00:00` (및 필요 시 子 전체)에 대해 **`calculateFourPillars`에 넣는 양력 일자를 +1일** 등으로 보정. |
| **시주** | 일간이 바뀌면 **五鼠遁**으로 시천간이 바뀔 수 있음. |
| **연·월** | `solarBirth`가 바뀐 일자 기준으로 **입춘·절입 월주** 재평가 필요 여부를 케이스별로 확인 (연말·입춘 인접 시). |
| **golden** | 토글별로 **케이스 분리** 또는 입력에 `yajaDayRoll: "same_day" \| "next_day"` 유사 필드 추가. |
| **API** | 요청에 모드 명시, 응답에 **적용된 모드** 포함 권장. |

---

## 4. 향후 구현 시 필요한 최소 분기 (설계만)

1. **입력 플래그** (예: `yajaNightZiDayRoll: "wiki_same_day" | "wiki_next_day"` 또는 위키 문구 그대로 `applied` / `not_applied`).
2. **`computePillarsKorean` 직전** (또는 내부 첫 단계):  
   - `wiki_same_day`(현재 동작과 동일): `birth` 그대로.  
   - `wiki_next_day`: KST 시각이 **해당 양력일의 23:30 이상**이면 `resolveSolarBirthDateParts` 결과의 **day(+ 필요 시 month/year)** 를 **익일**로 보정한 뒤 `calculateFourPillars` 호출.
3. **시주**: 보정 후 일간으로 기존 `calculateKoreanHourPillar` 유지 (子 23:30 경계는 그대로).
4. **골든**: `midnight-zishi-2001-0101-2340` 는 **미적용** 기대값과 엔진 **적용(당일)** 출력 차이를 명시한 채, 모드별 fixture로 분리하거나 `known_mismatch` 해제 조건을 정한다.

## 5. `known_mismatch` 와의 관계

| 케이스 | 상태 |
|--------|------|
| `midnight-zishi-2001-0101-2340` | `expected` 는 운세위키 **「미적용 (다음날)」** 측 QA 기둥(예: 일주 **을축**). 현재 엔진은 **당일 일주 유지** → **적용(당일)** 에 가깝다. |
| **정책이 “확정”된 것** | 위키 **두 모드**와 **子 23:30**; 엔진은 그중 **한 모드(적용)만** 구현. |
| **mismatch 성격** | 더 이상 “위키 규칙 자체 미확정”이 아니라, **골든이 잡은 기대가 위키 미적용 한쪽**이고 **엔진은 적용 쪽**이라서 생기는 **모드 불일치**로 정리하는 것이 맞다. |
| **해제 경로** | (A) 엔진에 **미적용** 분기 넣고 기대와 맞추거나, (B) 동일 입력에 **적용 모드 기둥**으로 `expected`·`known_mismatch` 를 갱신하거나, (C) **두 모드 각각** 활성 골든을 둔다. |
