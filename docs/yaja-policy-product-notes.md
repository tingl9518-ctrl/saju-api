# 야자시 정책 — 제품 옵션 검토 (문서만)

운세위키는 **야자시 적용 / 미적용**을 사용자가 고를 수 있다.  
따라서 목표는 “어느 쪽이 역사적으로 옳다”가 아니라, **우리 서비스에서 옵션으로 둘지·기본값을 무엇으로 할지**를 정하는 것이다.  
(본 문서는 **코드 변경 없음** — 현재 엔진 동작을 코드 기준으로 서술한다.)

---

## 1. 현재 엔진은 어떤 기준인가

### 일주(및 `manseryeok` 일간)

- `calculateFourPillars`에 넘기는 생년월일은 **양력 벽시계 연·월·일** 그대로이며, **23:xx대라도 달력 날짜를 바꾸지 않는다.**
- 즉 **일주는 “양력 자정(00:00)에서 날짜가 바뀌는” 일반 달력 기준**에 가깝다.
- 운세위키 **야자시 적용** 모드처럼 “23:30 이후 子는 **익일 일주**로 본다”는 귀속은 **하지 않는다.**

### 시주(한국형 30분 시진)

- `getKoreanShichenBranchIndex`: **23:30~익일 01:29** 구간을 **자시(子)** 로 본다.
- 시천간은 **그때의 일간(`pillars.day.heavenlyStem`)** 과 五鼠遁으로 정한다.
- 일간이 “자정 기준 당일”이므로, **23:40이면 여전히 전날 일간**을 쓴다 — 위키 **야자시 적용**에서 말하는 **익일 일간**과는 다를 수 있다.

### 한 줄 정리

| 구분 | 현재 엔진 |
|------|-----------|
| **일주 날짜 축** | **양력 자정(일반)** — 달력이 바뀌는 0시 기준 |
| **운세위키 “야자시 적용”** | **동일하지 않음** — 일주를 자시에 맞춰 익일로 굴리지 않음 |
| **운세위키 “야자시 미적용”** | **일주 측면**에서는 비슷한 쪽에 가깝지만, **시진 표(23:30 자시)** 는 위키 UI 토글과 1:1 대응이라고 단정할 수는 없음 |

---

## 2. 운세위키와 동일 UX를 가리면

### 설정 옵션으로 두는 것이 맞는지

- **맞다.** 위키가 이미 **적용 / 미적용**을 노출하므로, **동일한 선택지**를 두면 사용자 기대와 맞추기 쉽다.
- 대안은 “한 정책만 고정 + 도움말로 위키와 다를 수 있음”이지만, **비교·이주 사용자**에게는 옵션이 유리하다.

### 기본값은 무엇이 자연스러운지

- **시장·콘텐츠에 따라 다름.** 문서로만 제안하면:
  - **국내 만세력·위키를 그대로 따라가려면:** 위키와 같은 **기본값**(위키가 기본으로 켜는 쪽이 무엇인지 제품에서 한 번 더 확인)을 맞추는 편이 **체감 일치**에 유리하다.
  - **구현·회귀 단순화를 우선하면:** 현재 엔진과 동일한 쪽 = 사실상 **“미적용에 가까운 일주 귀속 + 기존 시진”** 을 기본으로 두고, **적용 모드는 옵션으로 추가**하는 식이 변경 범위를 줄일 수 있다.
- **확정은 PM/법무·운영 정책**으로 두고, 엔지니어링 문서에서는 “기본값 미확정”으로 남긴다 (`docs/qa-summary-milestone.md`의 미확정 정책과 동일).

## 3. 옵션화할 경우 영향 범위

| 영역 | 영향 |
|------|------|
| **일주** | **야자시 적용** 시, 특정 시각대(예: 전날 23:30~23:59 등 정의에 따라)에 **생일을 하루 당김/밀기**하여 `calculateFourPillars` 입력 일자를 바꿔야 함. |
| **시주** | 일간이 바뀌면 **五鼠遁**으로 **시천간 전체**가 바뀜. 시지(子)는 같아도 간이 달라질 수 있음. |
| **golden test** | 동일 입력에 **기둥이 두 갈래**이므로, fixture에 `yajaMode: "off"\|"on"` 같은 차원을 두거나 **케이스를 분리**해야 함. |
| **known_mismatch** | 정책이 코드에 반영되면 `midnight-zishi-2001-0101-2340` 등은 **한 모드에 맞춰 활성화**하거나, **양 모드 각각 golden**을 둘 수 있음. |
| **API payload** | 요청 JSON에 **`yajaNightZi` / `splitZiPolicy`** 등 불리언 또는 enum 추가, 응답에 **적용된 모드**를 넣어 재현성·CS 대응에 유리. |

연·월(절입·입춘)은 **생일을 양력으로 고정한 뒤**의 시각이므로, **일주만 바꾸는 정책**이면 연월 계산에 쓰는 `solarBirth`도 그 일자 기준으로 재평가할지(대부분 **동일 연도 내**면 월만 영향 가능) 설계 시 한 번 더 본다.

## 4. 구현 난이도

| 판단 | 근거 |
|------|------|
| **보통** (중간) | 단순 불리언 하나가 아니라, **일자 보정 규칙**(몇 시부터 익일 일주인지, 00:00~01:29 조자와의 관계)을 **명세로 고정**해야 하고, `computePillarsKorean` 단일 경로에 **모드 분기**가 들어간다. |
| 쉬움 아님 | 위키와 **픽셀 단위**로 맞추려면 **케이스별 QA**가 필요하다. |
| 어려움까지는 아님 | 라이브러리 교체 없이 **입력 일자 + 시각만 조건부 조정**으로 1차 구현은 가능한 편이다. |
