# Domestic reference 데이터 수집 — 자동화 가능성 조사

**목적:** 입춘 reference를 **운세위키 수동 조회**로 채우는 방식이 **1900~2100 규모에서 현실적인지**, **자동화·법적 리스크**를 정리한다.  
**범위:** 조사·판단만. **코드 구현 없음.**

관련: [`jieqi-qa-automation.md`](./jieqi-qa-automation.md)(CSV 필드·`source`), [`domestic-bundle-operations.md`](./domestic-bundle-operations.md)(Hybrid 병합), [`domestic-reference-priority.md`](./domestic-reference-priority.md)(연도 우선순위).

---

## 1. 현재 수작업 방식의 한계

### 1.1 규모 감각

| 구간 | 양력 연도 수(입춘 1행/년 가정) | 비고 |
|------|-------------------------------|------|
| **MVP (1970–2035)** | **66** | 현 `qa:jieqi:report`·번들 사주연과 정렬된 범위 |
| **1900–2100** | **201** | 제품이 “전 구간”을 약속할 때의 상한 |
| **12절 전량 domestic** | 201×12 ≈ **2,412**행(단순 곱) | `domestic-bundle-operations.md`에서 **비용 폭발**로 분류 |

### 1.2 예상 작업량(입춘만, 사람 기준)

전제: 연도마다 **위키 UI에서 입춘 창구·錨点 확인 → CSV `instantKst`·`note` 기입 →(선택) 스크린샷 보관**.

| 활동 | 보수적(분/년) | 낙관적(분/년) |
|------|---------------|----------------|
| 조회·기록·검수 | **10–20** | **3–5** |

| 구간 | 보수적 총시간 | 낙관적 총시간 |
|------|---------------|----------------|
| **66년** | 약 **11–22시간** | 약 **3.5–5.5시간** |
| **201년** | 약 **33–67시간** | 약 **10–17시간** |

**한계 요약**

- **1900~2100 전수**는 “불가능”은 아니나 **단일 엔지니어 부업**으로는 **일~주 단위 순공**이 나가며, **재검증·출처 감사**를 넣으면 **더 길어짐**.
- **위키 UI = 창구 그리드** vs CSV **錨点 한 점** 정의가 어긋나면 **같은 연도를 여러 번** 손봐야 함(`wiki-divergence-rules.md` §3).
- **윤달·야자시**까지 “위키와 동일”을 넓히면 **입춘 CSV만으로는 부족** — 수작업 표면적이 **기하급수**로 늘 수 있음.

**결론(§1):** MVP **66행**은 수작업으로 **현실적**. **201행**도 **분산·우선순위** 있으면 가능하나, **반복·실수·감사** 비용이 커져 **도구 없이 위키만**에 의존하는 것은 **장기적으로 취약**함.

## 2. 현실적인 자동화 가능성

### 2.1 운세위키 대상 자동 수집

| 수단 | 기술적 가능성 | 현실성 |
|------|----------------|--------|
| **HTTP 크롤링** | HTML/JSON 응답을 파싱해 연도별 입춘 근처 그리드 추출은 **원리상 가능** | **약관·차단·UI 변경** 리스크로 **제품 파이프라인에 넣기 어려움** |
| **브라우저 자동화**(Playwright 등) | CAPTCHA·로그인 유무에 따라 구현 난이도 가변 | 크롤과 동일하게 **“자동화된 수단”**으로 분류될 소지 — **§3과 결합 시 비추천** |
| **공개 API** | 일반 사용자용 **공식 입춘 bulk API**는 공개되어 있지 않다는 전제(조사 시점) | **사업 제휠·별도 계약** 없이는 **불가에 가깝다고 보는 것이 안전** |
| **DOM parsing** | 위키 프론트 구조에 강결합; **클래스·레이아웃 변경 시 파손** | **유지보수 부채** 큼 |
| **Rate limit / 차단** | Cloudflare 등 앞단이 있는 서비스에서 **흔함** | 저빈도라도 **패턴 탐지 시 IP·계정 제한** 가능 |

**robots.txt (https://luckyloveme.com/robots.txt, 조사 시점 스냅샷)**

- `User-agent: *`에 대해 **`Disallow: /api/`** 등 다수 경로 명시.
- “검색 인덱싱”과 **AI 학습용 봇**에 대한 **별도 User-agent 차단** 블록 존재.
- **일반 크롤러에게 모든 경로 허용**처럼 보이는 구간과 **약관상 금지**가 **동시에** 존재할 수 있어, **robots만으로 합법·계약 안전을 판단하면 안 됨**.

### 2.2 운세위키가 아닌 출처

| 출처 | 자동화 | 비고 |
|------|--------|------|
| **한국천문연구원(KASI) 역법·절기표** 등 | 공공·유료 **데이터 포맷**이 있으면 **스크립트로 변환**은 가능 | **이용약관·저작권·표기 의무**를 건별 확인. **위키 錨点과 수치가 다를 수 있음** — “위키 동일” 목표와는 **별 검증** 필요. |
| **구입 만세력·DB** | 벤더가 허용하는 범위 내 **배치 변환** | 비용·갱신 계약. |
| **사내 수동 표(OCR·스프레드시트)** | OCR 후 **사람 검수** + CSV 변환 스크립트 | **반자동**에서 가장 흔한 타협. |

## 3. 기술적·법적 리스크

### 3.1 서비스 약관 (운세위키)

**이용약관** (https://luckyloveme.com/terms, 조사 시점) **제10조 제1항** 예시:

- **제14호:** 회사 API 무단 도용, 리버스 엔지니어링·디컴파일 등으로 소스·알고리즘 추출 시도 **금지**.
- **제16호:** **자동화된 수단(봇, 크롤러, 스크래퍼 등)**으로 **과도한 요청** 또는 **시스템 부하**를 주는 행위 **금지**.
- 위반 시 **이용 제한**, 민·형사 책임·손해배상 조항(동조 제4항 등) 언급.

**판단 포인트**

- 문구에 **“과도한”**이 있으나, **저빈도 자동화가 허용되는지**는 **계약 해석·운영사 실무**에 달림. **제품용 무인 수집**을 걸기에는 **회색·고위험**.
- **브라우저 자동화**도 통상 **“자동화된 수단”**에 포함될 수 있어, **약관만으로도 자동 수집 파이프는 비권장**.

### 3.2 CAPTCHA·로그인

- 분석·결제·회원 기능이 붙은 구간은 **CAPTCHA·세션** 가능성이 있어 **무인 파이프 불안정**.

### 3.3 차단 가능성

- **동일 IP·헤더 패턴**의 반복 요청 → **WAF/레이트 리밋**.
- **ToS 위반**으로 계정·IP 영구 제한 시 **운영·법무 리스크**.

### 3.4 유지보수

- **DOM 구조 변경** → 셀렉터 전부 파손.
- **위키 錨点 정의**(창구 vs 한 시각)가 바뀌면 **파서가 “틀린 확신”**을 CSV에 씀 — **자동화가 오히려 위험**.

## 4. 현실적인 추천 방향(비교)

| 방향 | 설명 | 운세위키 자동 수집 |
|------|------|-------------------|
| **완전 자동화** | 무인으로 66~201년 채움 | **약관·신뢰성·유지보수**상 **비추천** |
| **반자동** | 사람이 **錨点·출처 확정**; 기계는 **병합·diff·리포트·포맷 변환** | 위키는 **브라우저로 사람이 읽기**; 레포에는 **스크립트 없음 또는 오프라인만** |
| **핵심 연도만 수동** | `domestic-reference-priority.md`의 outlier·앵커 위주 | **비용 대비 효과 최대**; 나머지는 시드 유지 |
| **Hybrid** | lunar-js 시드 + **CSV override 병합**(운영 문서대로) | CSV 내용의 **입수**만 사람/공인 데이터; **위키 크롤은 파이프에 넣지 않음** |

## 5. 지금 프로젝트 규모에서 **가장 현실적인 방법 1가지**

**추천: 반자동(Hybrid의 “데이터 층”만 엄격히 사람·공인 출처로 한정)**

1. **입춘 錨点·창구**는 **운세위키를 “사람이 브라우저로 확인”**하거나, **KASI·구입 DB 등 약관상 허용된 표**에서 가져와 **같은 스키마로 CSV에만** 기록한다.  
2. **레포·CI에 운세위키 크롤러·비공식 API 클라이언트를 두지 않는다.** (법무·운영 단순화)  
3. **기계 자동화**는 이미 설계된 축에만 둔다: **`qa:jieqi:report`**, (도입 시) **시드 빌드 + CSV 병합**, **`source` / `verifiedBy` / `note`**.  
4. **201년 전수**가 필요해지면, **위키 전수 크롤이 아니라** **공인 절기표 일괄 라이선스 + 변환 스크립트(오프라인)** 또는 **10년 단위 수동 배치**를 로드맵에 둔다.

**한 줄:**  
**“위키 맞추기”는 소량·우선순위로 **사람이 읽고 CSV에 쓰는 것**이 현실적이고, **위키를 기계가 긁는 완전 자동화는 이 프로젝트 규모·약관 환경에서 추천하지 않는다.**
